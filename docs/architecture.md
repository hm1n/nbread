# 엔빵 v2 초기 구조

## 목표

금융 앱의 입금 알림을 받아 정산 후보를 만들되, 잘못된 자동 정산을 막는 일을 가장 먼저 지켜요. 첫 입금과 애매한 거래는 사용자가 직접 확인해요.

## 처리 흐름

```text
Android 알림 수집 또는 iOS 단축어
  → 알림 접수 API
  → notification_events 저장과 큐 등록
  → 비동기 처리 작업
  → 규칙 파싱과 필요할 때만 인공지능 파싱
  → 원문 대조와 중복 확인
  → 정산 조건 확인
  → 자동 반영 또는 확인 대기
```

알림 접수 API는 파싱과 정산을 수행하지 않아요. 접수 기록을 저장하면 데이터베이스 트리거가 같은 작업 안에서 큐 메시지를 만들어요. 저장이 실패하면 큐 등록도 함께 취소돼요.

## 지금 확정한 선택

| 영역 | 선택 | 이유 |
| --- | --- | --- |
| 웹 | Next.js App Router와 TypeScript | 기존 엔빵 구조와 작업 방식을 이어가요. |
| 데이터 | Supabase PostgreSQL과 RLS | 기존 인증과 데이터를 재사용해요. |
| 비동기 처리 | Supabase Queues | 초기 운영 요소를 늘리지 않고 접수와 처리를 나눠요. |
| 입력 검증 | Zod | 기기와 서버가 공유할 알림 규격을 엄격히 검사해요. |
| 모바일 껍데기 | Capacitor | 기존 웹 화면을 재사용하고 Android 네이티브 수집 기능을 따로 만들 수 있어요. |
| Android 수집 | Kotlin 서비스와 Room, WorkManager | 웹 화면과 상관없이 알림을 받고 실패한 전송을 다시 시도해요. |

## 아직 확정하지 않은 선택

원격 웹 화면은 개발 중 시험에만 써요. 연결할 수 없을 때 보여 줄 최소 화면은 앱에 넣어 두었어요. 운영 적용 전에는 허용 주소, 콘텐츠 보안 정책, 브리지 입력, 버전 호환, 서버 장애 화면, 앱 심사를 확인해야 해요.

인공지능 모델과 공급자는 실제 금융 앱 알림 평가 자료를 만든 뒤 정해요. 정산 변경 권한은 모델에 주지 않아요.

iOS 지원 범위는 잠금 상태에서 단축어가 서버 전송을 안정적으로 수행하는지 확인한 뒤 정해요.

## 다음 구현 순서

1. 기존 저장소의 데이터 구조와 정산 흐름을 이 저장소로 옮겨요.
2. 실제 Android 금융 앱 알림을 모아 허용 앱 목록과 기기 쪽 최소 수집 규칙을 정해요.
3. 큐 처리 작업과 상태 전이를 만들어요.
4. 은행별 규칙 파서와 평가 자료를 만들어요.
5. 그룹원, 별칭, 거래, 정산 연결, 변경 기록을 기존 표에 맞춰 추가해요.
6. 최초 확인 화면과 확인 대기 화면을 만들어요.

## 지켜야 할 조건

알림 원문과 기기 토큰은 로그에 남기지 않아요. 기기 토큰은 해시만 저장해요. 원문 알림 표는 서버 전용 권한으로만 읽어요. 같은 기기와 이벤트 식별자가 다시 오면 새 큐 작업을 만들지 않아요. 거래와 정산 연결에는 데이터베이스 고유 조건과 작업 묶음을 사용해 중복 반영을 막아요.
